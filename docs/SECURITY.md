# Security

## Reporting

Open a GitHub security advisory on the repository, or email the maintainer. Do
not open a public issue for an unfixed vulnerability.

## What this service holds

| Data | Where | Sensitivity |
|---|---|---|
| Account email and password hash | D1 `users` | Personal data; password is PBKDF2-SHA256 with a per-account salt |
| Session ids | D1 `sessions` | Keyed hashes of the cookie value, not the cookie |
| Bludit API token, user auth token, Wizard key | D1 `sites`, AES-256-GCM | **Full control of a customer's website** |
| OAuth grants, codes, refresh tokens | KV | Ability to obtain access tokens |
| Page content | Nowhere persistent | Passes through a tool result and is gone |
| Audit trail | D1 `audit_log` | Which tool ran, when, for which account and site. No content, no credentials. |

The credential columns are the crown jewels: a leaked Bludit API token plus auth
token gives write access to a live website.

## Controls

### Credentials at rest

AES-256-GCM, WebCrypto, key from the `SITE_CREDENTIAL_KEY` Worker secret. The
site id is the additional authenticated data, so a ciphertext lifted from one row
cannot be decrypted as another. A fresh 96-bit IV per value means two sites
sharing a token produce different ciphertexts.

Plaintext exists only inside a single request: it is decrypted, used for one
outbound call, and discarded. It is never written to D1, logged, returned by a
tool, or included in an error.

The root key is a Worker secret, which means it is not in the config file, not in
the database, and not in the repository. Wrangler cannot read it back, so a copy
must be kept in a password manager — losing it makes every stored credential
undecryptable.

### Ownership verification before storing a credential

A pasted API token is never accepted as proof that the caller owns a site. A
connection requires three independent things:

1. A signed-in account.
2. A single-use pairing challenge generated by that account, stored only as an
   HMAC, with a 15-minute default lifetime.
3. Site-side proof: either an HMAC proof from the Bludit Wizard extension, keyed
   by the GPT Action key, or the challenge published verbatim at
   `/.well-known/bludit-wizard-challenge.txt`.

Comparison is constant-time in both cases. The challenge is consumed **last**, so
a failed store leaves it usable rather than burning it.

### Identity and authorization

Authorization is decided from the validated access token, never from tool
arguments or from anything a model wrote:

- `ctx.auth.scope` and `ctx.props.userId` come from the token the authorization
  server validated over a private Service Binding.
- Every tool re-checks its own scope inside its callback, in addition to the HTTP
  pre-flight, so a bug in one layer does not authorise a write.
- Every site lookup is scoped by `user_id`. Another account's site id returns
  `not_found`, not `forbidden`, so the API cannot be used to discover that a site
  exists elsewhere.
- Every proposal lookup is scoped by both `user_id` and `site_id`.

A 403 challenge names the **complete** scope set an operation needs. The baseline
read scopes are included in every challenge, so a client cannot end up holding
`pages:write` without `pages:read`.

### Scope model

| Scope | Grants |
|---|---|
| `sites:read` | List and resolve connected sites, read capabilities |
| `pages:read` | Read pages, drafts, tags, categories |
| `pages:write` | Create and edit pages, propose and apply edits |
| `settings:read` | Read site settings (site title, description, language) |
| `offline_access` | A refresh token |

No scope grants deletion, because no tool performs it.

### Audit trail

Every tool call writes one row: the account, the site, the credential that acted,
the tool, an outcome of `ok` / `denied` / `error`, and — on failure — a stable error
*code* rather than a message, because a message could carry upstream text.

The credential is recorded as either the OAuth `client_id` or `pat:<id>`, so the
two are never conflated and either can be revoked without the other. A test asserts
that the trail contains no credential, no page content and no site label, and that
every row is scoped to an account.

### Pagination and revision safety

`proposals.base_revision` is a hash of the fields a write can change. `apply_approved_edit`
re-reads the page and refuses if the revision moved. `edit_page` accepts an
optional `expected_revision` for the same protection on the direct path. This
defeats the "approve a diff, then silently overwrite a newer edit" failure mode.

### Rate limiting

Every public entry point is bounded. This was the one accepted risk that
genuinely blocked a public deployment, and it is implemented and tested (42
tests).

| Bucket | Principal | Default | Protects |
|---|---|---|---|
| `signin` | address **and** email | 10 / 15 min | Credential brute force |
| `authorize` | address | 240 / hour | Authorization-request floods |
| `token` | address and client | 240 / hour | Token-endpoint abuse, including revocation requests |
| `register` | address | 10 / hour | Dynamic Client Registration spam |
| `pairing` | account | 20 / hour | Pairing-challenge floods |
| `connect` | account | 30 / hour | Repeated connection attempts, successful or not |
| `mcp` | account and client | 300 / min | Tool-call abuse, per client rather than per account |
| `mcp_account` | account | 600 / min | Aggregate load on a customer's site, however many clients the account authorized |
| `signup` | address | 5 / hour | Account-creation abuse: the most expensive unauthenticated endpoint on the service |
| `pat_create` | account | 30 / hour | Minting long-lived credentials |
| `consent` | account | 120 / hour | Accepting authorization requests, each of which writes a grant |
| `site_check` | account | 60 / hour | Outbound amplification pointed at a customer's own site |

Every bucket is overridable per deployment with `RL_<NAME>` in
`"<limit>/<windowSeconds>"` form, so no limit needs a code change to adjust.

**Deliberately not rate limited**, recorded so the gaps are choices:

| Endpoint | Why not |
|---|---|
| `POST /clients/:id/revoke` | A safety action. A user who cannot revoke a leaked client is worse off than the abuse a limit would prevent. |
| `POST /tokens/:id/revoke` | Same, and more so: this is how a leaked token is stopped. A test asserts ten revocations in a row are all accepted. |
| `GET /signout` | Ends a session. Limiting it helps nobody. |
| `GET /healthz` | A liveness probe. A limit would make monitoring report an outage. |
| `GET /.well-known/*` | Public static metadata that a client must reach before it has any credential. |
| `GET /`, `/signin`, `/signup`, `/sites`, `/clients`, `/tokens` | Form and list renders. Every mutating verb is bounded. |

Design properties that matter:

- **Counters are global, not per-colo.** They live in D1 because KV allows one
  write per second to the same key and is eventually consistent, and because an
  in-memory counter gives an attacker a fresh budget per isolate. ADR-011 records
  the trade-off.
- **No personal data is stored.** A bucket is
  `category:HMAC-SHA256(secret, identifiers)`, so a database leak reveals counts
  and not identities. A test asserts that no IP address, no email address and no
  plain identifier appears in the table.
- **A refused request is still counted**, so a persistent client does not get a
  free pass at the start of the next window.
- **A malformed limit falls back to the default** rather than parsing as zero,
  which would deny every request.
- **Sign-in refusals are byte-identical for a real and an invented account**, so
  the limiter cannot be used to enumerate accounts. A test asserts this.
- **Storage failure fails open** and logs. D1 being unavailable already breaks the
  service, so failing closed would turn a partial outage into a total one without
  improving security.
- **A `429` carries `Retry-After`**, plus `x-ratelimit-limit`,
  `x-ratelimit-remaining` and `x-ratelimit-reset`. The token and registration
  endpoints return an OAuth-shaped body; everything else returns plain JSON.

Cloudflare's Rate Limiting binding is a cheaper, per-colo mechanism and is
documented in `ARCHITECTURE.md` as an optional additional layer. It is not the
mechanism here because it cannot be exercised from the test harness, and an
untested control is not a control.

### SSRF

Four layers, in order of strength:

1. **Runtime.** Both Workers set `global_fetch_strictly_public`, so workerd
   refuses to connect to private or non-public addresses even if the code below
   is wrong. This is the layer that covers DNS rebinding, which no static check
   can.
2. **Static policy** (`src/shared/ssrf.ts`). HTTPS required; no embedded
   credentials; no fragment; IPv4 and IPv6 literals in reserved ranges rejected,
   including `::ffff:0:0/96`, `64:ff9b::/96` NAT64 and `2002::/16` 6to4 forms
   with their embedded IPv4 checked; internal-only hostnames rejected. Obfuscated
   IPv4 literals (`2130706433`, `0x7f000001`) are normalised by the URL parser
   before the range checks see them.
3. **Redirect policy.** `redirect: 'manual'` and every `Location` revalidated, so
   a public host cannot bounce the request inward.
4. **Response bounds.** Timeouts, a redirect cap, and a maximum body size, so a
   hostile or broken site cannot exhaust the Worker.

Loopback is permitted **only** when `ALLOW_INSECURE_SITE_URLS=true`, and only for
loopback — never for a LAN address. That flag exists for local development and is
tested as refused under the production-shape profile.

### Browser session and CSRF

- Session cookie is `__Host-` prefixed on https (Secure, Path=/, no Domain),
  `HttpOnly`, `SameSite=Lax`.
- The session id stored in D1 is an HMAC of the cookie value, so a database leak
  does not yield a usable session.
- Sessions are bound to the user agent that created them.
- CSRF tokens are derived from the session token, so they are unguessable without
  reading the victim's cookie and need no second cookie.
- `SameSite=Lax` blocks cross-site POSTs independently.
- `safeNext` accepts only same-origin absolute paths, so `?next=` cannot become
  an open redirect.

### OAuth

- Authorization Code with **PKCE required** (`S256`), refresh tokens with idle
  expiry, revocation, DCR and CIMD.
- Redirect URIs must be `https`, or `http` on loopback. Remote plain `http` is
  refused, and a registration callback rejects it at registration time.
- An unregistered redirect URI produces a locally rendered error, never a
  redirect to the attacker.
- A remembered consent is bound to the client, the redirect URI, the resource
  **and** the account, so approving one client on a shared browser does not
  approve another.
- Access tokens are audience-checked against the canonical resource by the
  validator.

### Secrets handling in code

- `src/shared/log.ts` redacts any field whose key matches
  `token|secret|password|authorization|apikey|credential|cookie`, and scrubs
  credential-shaped substrings from every string value.
- `src/shared/errors.ts` maps unexpected errors to a generic `internal_error`, so
  a message can never carry a secret upward.
- Upstream error bodies are never returned verbatim; only a truncated, redacted
  message.
- `audit_log.detail` holds an error *code*, never a message.

### Repository hygiene

- `.gitignore` covers `.dev.vars`, `.env*`, `*.pem`, `.wrangler/`, `reports/`.
- No secret, token, hostname or credential appears anywhere in the repository.
  `.dev.vars.example` contains variable names and empty values only.
- CI has no credentials and no deploy step.

## Why page deletion is not exposed

This is a deliberate policy decision, not an unimplemented feature.

- **It is irreversible.** Bludit has no trash or soft delete, and the API's
  `DELETE /api/pages/<key>` removes the page directory and its database row.
- **It is destructive at a scale an agent can reach by accident.** "Clean up the
  drafts" is a plausible instruction that could delete real content.
- **No client needs it.** Every published MCP use case for Bludit is authoring:
  draft, edit, publish. Deletion belongs in the Bludit admin UI, where the user
  sees what they are removing.
- **The upstream stdio server exposes it.** That is a real difference between the
  two, and it is documented in `UPSTREAM_COMPARISON.md`. The hosted server does
  not inherit the exposure.

The `DELETE` endpoint remains available in the PHP Wizard API and in the official
Bludit API. Neither this server nor any of its tools calls it.

Reconsidering this would require, at minimum: a recoverable delete (a trash key
the CMS can restore), a separate scope that is never granted by default, an
explicit per-call confirmation carrying the page's current revision, and a
documented review. None of that exists today.

## Findings

### Fixed during development, found by the test suite

These were real defects in this codebase, caught before deployment. Each has a
regression test.

| Severity | Issue | Fix |
|---|---|---|
| High | `::ffff:127.0.0.1` and `[::ffff:169.254.169.254]` were **accepted** by the SSRF policy. The IPv4-mapped embedded address was never extracted, so the reserved-range check never ran. | Rewrote the IPv6 parser to strip the embedded dotted-quad and treat it as the two trailing hextets. |
| High | `64:ff9b::/96` (NAT64) and `2002::/16` (6to4) prefixes were matched with a helper that shifted both operands twice, so `::ffff:0:0/96` and every other prefix comparison was wrong. | Replaced with a correct top-*n*-bit mask. |
| Medium | The remembered-consent `Set-Cookie` was dropped: the consent decision response rebuilt its `Headers` from the existing object, and the cookie did not survive. Remembered consent silently never worked. | Mutate the returned `Headers` instead of copying it. |
| Medium | The `403 insufficient_scope` challenge named only the *missing* scopes. MCP clients treat that list as exhaustive, so a client stepping up from `pages:read` to a write would have requested `pages:write` alone and still been refused. | The challenge now names the complete required set, including the baseline. |
| Low | `edit_page` did not report whether the page body changed, only metadata fields, so a body-only edit looked like a no-op. | Added `contentChanged`. |
| Low | A 404 on `/api/pages` was reported as `not_found` ("the page does not exist") when it actually means the API plugin is disabled. | Added `capability_unavailable` for endpoint-level 404s. |
| Low | The mock's tag listing used a malformed Set construction (`Array#flat` in the wrong place), which also revealed that the tool could not distinguish tag arrays from comma-joined strings. | Fixed both. |
| Medium | Every `/sites` route dereferenced `session.user` without checking for a session, so an unauthenticated visit returned a 500 rather than redirecting to sign in. Found by the first browser test written against those pages. | Added a session guard middleware over `/sites` and `/sites/*`. |
| **High** | **Four expensive or sensitive endpoints were entirely unprotected**: `POST /signup`, `POST /tokens`, `POST /authorize/decision` and `POST /sites/:id/check`. `POST /signup` is reachable with no credential at all and each request runs PBKDF2 plus a database write, making it a CPU and storage abuse vector; `POST /sites/:id/check` makes four or five outbound requests to a customer's own site, making it an amplifier pointed at them. Found by the pre-deployment rate-limit audit. | Added `signup`, `pat_create`, `consent` and `site_check` buckets, plus `mcp_account` for aggregate load. Revocation is deliberately left unbounded, and a test asserts that. |
| High | `tags` is a comma-joined **string** on the wire, not an array. `search_pages` and `get_related_pages` called `.some()` on it and threw, returning `internal_error` on a real site; `summarizePage` discarded every page's tags. Found by the first live test run against real Bludit. | Added `pageTags()` and used it in every tag read. The mock was the thing that was wrong, and it now reproduces the real representation. |
| Medium | `category` is `false`, not a string, when a page has no category or when its stored category is not one the site defines. `search_pages` threw `false.toLowerCase is not a function`. Found by the same live run. | Added `pageCategory()`, typed the field as `string \| false`, and documented that the `category` write argument is inert unless the category exists. |

### Accepted risks

| Risk | Assessment | Mitigation in place |
|---|---|---|
| **Both Workers share `SITE_CREDENTIAL_KEY`.** | The resource server must decrypt credentials to call the CMS, and the authorization server must encrypt them at connection time. Splitting the key would require the authorization server to proxy every CMS call. | The key is a secret, the shared D1 database is already a coupling, and the alternative is a much larger trust surface. Documented in `ARCHITECTURE.md`. |
| **KV is eventually consistent.** | Revoking a grant may not take effect everywhere instantly. KV propagates globally in up to 60 seconds. | Tokens have a one-hour TTL, so the window is bounded. Security-critical revocation could move to D1 or Durable Objects if it ever matters. |
| **No MFA on service accounts.** | An account controls the websites connected to it, so account takeover is website takeover. | Email and password only, with brute-force protection. Listed below as a public-launch blocker. |
| **No password reset by email.** | A user who forgets a password has no route back in. | Needs an email provider, which is a new external service and needs an approval. Listed below as a public-launch blocker. |
| **No alerting.** | Abuse or a failure spike is visible in the Cloudflare dashboard but pages nobody. | Structured logs, an audit table, and `429` metrics exist; no notification channel is configured. |
| **The platform SSRF layer cannot be probed locally.** | Miniflare does not enforce `global_fetch_strictly_public`, so the runtime layer is verified by configuration and by post-deployment checks rather than by the test suite. | The URL-policy layer is load-bearing and is tested accordingly; a test documents the gap so it cannot be mistaken for coverage. |
| **`get_website_settings` requires an admin auth token.** | Bludit gates `/api/settings` behind an authenticated admin, so this one tool needs more than the read-only token. | The tool is scope-gated separately (`settings:read`) and the capability report tells the user when the auth token is missing rather than failing opaquely. |
| **The Wizard pairing contract is proposed, not implemented.** | Sites today use the ownership file unless the extension gains `/pair`. | The ownership file is a complete, plugin-free path. The proposed contract is in `PHP_WIZARD_INTEGRATION.md`. |
| **Credential key rotation is unimplemented.** | Rotating `SITE_CREDENTIAL_KEY` currently requires reconnecting every site. | `CREDENTIAL_KEY_VERSION` is recorded on each grant, so staged rotation is possible later. |
| **`/api/users` and upload endpoints are never probed.** | A site could have them disabled and this server would not know. | Deliberate: probing `/api/users` would disclose account records, and probing uploads would perform an upload. Reported as `documented`, not `supported`. |
| **Account passwords are the only second factor.** | No MFA on this service's own accounts. | The accounts are self-hosted and the blast radius is the connected sites. MFA is on the hardening list. |

## Deployment classification

Not every accepted risk blocks the same thing. Splitting them is the difference
between a usable internal deployment and a defensible public one.

### Does not block a first development deployment

- Both Workers share `SITE_CREDENTIAL_KEY`. Required for the resource server to
  decrypt; the alternative is proxying every CMS call.
- KV eventual consistency on revocation, bounded by the one-hour access-token TTL.
- The platform SSRF layer being unprobeable locally.
- `get_website_settings` needing an admin auth token — Bludit's own rule.
- The Wizard pairing contract being proposed rather than implemented.
- Only 3.22.0 being live-verified.

### Blocks a public launch

1. **No MFA on service accounts.** Credential stuffing on a password-only login is
   the most likely route to a connected website.
2. **No password reset.** A locked-out user is a support incident with no
   resolution.
3. **No MCP client verified.** The protocol is proven; no product has been
   connected. This is the largest gap in the publication case.
4. **No alerting.** Abuse and failures are visible but nobody is told.
5. **No credential key rotation.** A suspected key compromise currently means
   reconnecting every site by hand.
6. **No `/.well-known/security.txt`.** Needed for coordinated disclosure.

### Remaining work, in priority order

1. **MFA** on service accounts, and a password reset path. Both need an email
   provider for a proper implementation, which is a new external service and an
   approval.
2. **Verify one real MCP client** and record the result in
   `CLIENT_COMPATIBILITY.md`.
3. **Credential key rotation** using `CREDENTIAL_KEY_VERSION`, which every grant
   already records.
4. **Alerting** on `429` volume, Worker errors and D1 write growth.
5. **`/.well-known/security.txt`**, and a published disclosure address.
6. **A second look at revocation latency** if immediate revocation becomes a
   requirement, which would mean moving token records to D1 or Durable Objects.

## Verification status

Everything above is asserted by the test suite: **428 tests** —
222 unit, 164 integration in real workerd, 9 compatibility across modelled Bludit
variants, 24 against real Bludit installations, and 9 in a real browser. Two
`RATE_LIMIT_ENABLED=false` test profiles keep every other suite independent of the
production limits, while `production-config.test.ts` asserts the deployable configs
do not disable them. `docs/TEST_REPORT.md` records what was measured and on which
commit.

Things that are **not** verified and are not claimed:

- **No MCP client has been used end to end.** The OAuth and MCP flows are driven
  by a purpose-built client in the test harness that follows the specifications,
  not by ChatGPT, Claude, Codex, Gemini CLI or OpenCode. See
  `docs/CLIENT_COMPATIBILITY.md`. This is a public-launch blocker.
- **The live Bludit installations are loopback over plain http**, reached through
  the development allowance. The production SSRF policy and TLS are therefore not
  exercised by the live runs.
- **The Wizard extension has not been live-tested.** Its pairing path is verified
  against a faithful mock of the proposed contract.
- **Nothing is deployed.** None of this has run on Cloudflare.
